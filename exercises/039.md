# 039 — Bit-fields

Implement `uint8_t encode_permissions(Permissions p)` and
`Permissions decode_permissions(uint8_t byte)` in `039.c`.

`Permissions` is a struct of bit-fields:
`typedef struct { unsigned read : 1, write : 1, execute : 1, level : 5; } Permissions;`.
Each member occupies the stated number of bits, so `read`, `write` and
`execute` hold `0` or `1` and `level` holds `0`–`31`.

`encode_permissions` packs the fields into one byte with this fixed layout:

| bits | field     |
| ---- | --------- |
| 0    | `read`    |
| 1    | `write`   |
| 2    | `execute` |
| 3–7  | `level`   |

So `byte = read | write << 1 | execute << 2 | level << 3`.
`decode_permissions` is the exact inverse: mask and shift each field back out
(`level = (byte >> 3) & 0x1F`). Every byte value round-trips.

Why not `memcpy` the struct into a byte, or use a union? Because the C
standard leaves the *order* and *packing* of bit-fields to the
implementation: whether `read` lands in the low bit or the high bit, whether
fields can straddle storage units, even `sizeof(Permissions)`. GCC on x86
puts the first field in the lowest bit; other ABIs differ. Bit-fields are
fine for in-memory flags inside one program, but anything that goes on the
wire or to disk must be packed with explicit shifts and masks. That is the
lesson of this exercise, and why the two functions exist at all.

Allowed: shifts, masks, nothing else. Do not read the struct's bytes
directly.

Examples: `{read=1, write=0, execute=1, level=0}` → `0x05`;
`{1,1,1,31}` → `0xFF`; `{0,0,0,0}` → `0x00`; `{0,1,0,5}` → `0x2A`;
`decode_permissions(0x2A)` → `{read=0, write=1, execute=0, level=5}`.
