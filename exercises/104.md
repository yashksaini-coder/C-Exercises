# 104 — Mutex-protected state

Implement `SafeCounter *safe_counter_new(void)`, `void safe_counter_add(SafeCounter *counter, long amount)`,
`long safe_counter_get(SafeCounter *counter)` and `void safe_counter_free(SafeCounter *counter)`
in `104.c`.

`SafeCounter` is opaque (defined only in `104.c`): a `long` value plus a
`pthread_mutex_t` that guards it. Several threads will call
`safe_counter_add` at the same time, and the final value must be exact.

Contract:

- `safe_counter_new()` allocates a counter at `0` with an initialised mutex
  (`pthread_mutex_init`); returns `NULL` if `malloc` or the init fails.
- `safe_counter_add(c, amount)` locks, adds, unlocks.
- `safe_counter_get(c)` locks, reads, unlocks, returns the value. Yes, even
  a read needs the lock: a plain read racing with a write is undefined
  behaviour, whatever the hardware happens to do.
- `safe_counter_free(c)` destroys the mutex (`pthread_mutex_destroy`) and
  frees the memory; `NULL` is a no-op.

Why it matters: `value += 1` is three steps (load, add, store). Two threads
interleaving those steps lose updates, so 8 threads each adding 1 ten
thousand times usually end at *less* than 80000 without the lock. Try it:
comment the lock out and run `make test N=104` a few times. The test checks
for exactly 80000, so the racy version fails most runs, and
`SANITIZE=1` with ThreadSanitizer (`-fsanitize=thread`, not enabled by the
Makefile because it conflicts with AddressSanitizer) reports the race
deterministically.

No global state: the mutex lives inside the struct. No atomics here (that
is 106); the lesson is the critical section.

Examples: a fresh counter → `safe_counter_get` is `0`; after `add(5)` and
`add(-2)` → `3`; 8 threads × 10000 × `add(1)` → `80000`;
`safe_counter_free(NULL)` → nothing.
