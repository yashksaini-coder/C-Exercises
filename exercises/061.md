# 061 — Opaque types

Implement `Counter *counter_new(int start)`, `void counter_increment(Counter *counter)`,
`int counter_get(const Counter *counter)` and `void counter_free(Counter *counter)`
in `061.c`.

`include/exercises.h` only says `typedef struct Counter Counter;`. That is an
*incomplete type*: callers can hold a `Counter *` but cannot see inside it,
take its `sizeof`, or declare a `Counter` on the stack. The full definition
`struct Counter { ... }` lives in `061.c` alone. This is how C does
encapsulation: the header is the public interface, the `.c` file owns the
representation, and you can change the struct layout later without
recompiling callers.

Contract:

- `counter_new(start)` allocates a counter with `malloc` whose value is
  `start`; returns `NULL` if allocation fails.
- `counter_increment(c)` adds one to the value.
- `counter_get(c)` returns the current value.
- `counter_free(c)` releases the memory; `counter_free(NULL)` is a no-op,
  like `free(NULL)`.

Every call is given a valid counter unless stated otherwise. Keep the value as
an `int`; no global state, one `malloc` per counter.

Examples: `counter_get(counter_new(5))` → `5`; after three
`counter_increment` calls on a counter started at `-2` → `1`;
`counter_free(NULL)` → nothing happens.

> [!TIP]
> Read: Beej's Guide to C, §35 Incomplete Types —
> https://beej.us/guide/bgc/html/split/incomplete-types.html
> C++ interviewers ask "how do you hide implementation details in C?": the
> answer is this exact pattern (the "pimpl" idiom in C++ comes from it).
