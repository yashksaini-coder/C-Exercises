# 096 — Length-prefixed framing

Implement `int send_frame(int fd, const void *payload, uint32_t length)` and
`ptrdiff_t recv_frame(int fd, void *buffer, size_t capacity)` in `096.c`.

Because TCP has no message boundaries (see 095), protocols add their own.
The simplest is a length prefix: every frame is a 4-byte big-endian
(network byte order) unsigned length followed by exactly that many payload
bytes. The receiver reads 4 bytes, decodes the length, then reads that many
more.

`send_frame` writes the 4-byte header then the payload, looping over
partial sends exactly as in 094. Return `0` on success, `-1` on error. An
empty frame (`length == 0`) is valid and sends just the header.

`recv_frame` reads one frame into `buffer`:

- Returns the payload length (`0` for an empty frame) on success, with the
  payload bytes in `buffer`. The buffer is *not* NUL-terminated.
- Returns `-3` on clean EOF: the peer closed before sending any byte of a
  header. This is how a well-behaved connection ends.
- Returns `-1` on a `recv` error, or on EOF in the middle of a header or
  payload (a truncated frame).
- Returns `-2` when the decoded length exceeds `capacity`. Read and
  discard nothing: the payload is left unread on the socket, so the caller
  should close the connection.

Encode and decode the header with shifts (as in 055/056) or `htonl`/`ntohl`
with `memcpy`; never cast the buffer to `uint32_t *`.

Each exercise is compiled on its own, so `send_all` (094) and `recv_exact`
(095) are *not* linked into this one. Either copy them into `096.c` as
`static` helpers, or move them into `lib.c` (declare them in `lib.h`, remove
them from `094.c`/`095.c`) so every exercise can use them. Do not leave two
definitions of the same name in a build.

Examples: `send_frame(fd, "hello", 5)` writes bytes
`00 00 00 05 68 65 6C 6C 6F`; `recv_frame` on the other end → `5`, buffer
`"hello"`; `send_frame(fd, "", 0)` then `recv_frame` → `0`; peer sends
`00 00 10 00` (4096) into a 64-byte buffer → `-2`; peer closes with nothing
pending → `-3`; peer sends `00 00 00 05 68 69` then closes → `-1`.
