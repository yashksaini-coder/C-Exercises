# 106 — Atomics

Implement `void atomic_hits_reset(void)`, `void atomic_hit(void)` and
`long atomic_hits(void)` in `106.c`.

A hit counter that many threads bump at once, with no mutex. Keep one
file-scope `static _Atomic long` (or `atomic_long`) and:

- `atomic_hit()` adds 1 with `atomic_fetch_add(&hits, 1)` (or `hits++`,
  which is atomic on an `_Atomic` object), so concurrent increments never
  lose an update.
- `atomic_hits()` returns the current count (`atomic_load`).
- `atomic_hits_reset()` stores `0` (`atomic_store`), so the tests can start
  from a known state.

This is the one exercise in the track where a file-scope variable is the
point: the lesson is that `static long hits; hits++;` from several threads
is a data race (undefined behaviour; in practice lost updates), and that
declaring the object `_Atomic` turns each `++` into a single indivisible
read-modify-write. No `pthread_mutex_t` here; no other global state.

The default memory order (`memory_order_seq_cst`) is fine. If you want to
try `memory_order_relaxed` for the increment, it is correct for a pure
counter because nothing else depends on the order; say so in a comment.

Examples: after `atomic_hits_reset()` → `atomic_hits()` is `0`; three
`atomic_hit()` calls → `3`; 8 threads × 10000 `atomic_hit()` → `80000`;
`reset` then `hit` → `1`.

> Interviewers ask "mutex or atomic?"; the answer is: atomic for a single
